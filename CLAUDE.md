# circle-saas (CLAUDE.md)

サークル会計 SaaS (仮名)。**大学サークル向け立替精算ワークフロー特化のマルチテナント SaaS**。SaaS 固有の仕組み (auth / billing / multi-tenant / onboarding) 習熟が一番の目的。

> 構想・要件・アーキ・ロードマップは `docs/` 配下 (REQUIREMENTS / ARCHITECTURE / ROADMAP)。詳細仕様はここ参照。
> 設計判断は `docs/decisions/` に ADR として残す (`docs/decisions/README.md` 参照)。
> `docs/` は track 対象。一時メモだけ `docs/memo/` に置いて git ignore。

## Stack 一覧

```
Runtime:    Bun (1.3+)
BE:         Hono (API) + Drizzle ORM + better-auth
DB:         Turso (libSQL, DB per tenant pattern)
              - Central DB: circle-saas-central (users / tenants index / billing)
              - Tenant DB: 各サークル作成時に programmatic 作成 (expenses など)
FE:         React 19 + TanStack Router (file-based) + Vite 8
UI:         HeroUI v3 + Tailwind v4 (CSS-first、@import "tailwindcss" + @import "@heroui/styles")
State:      TanStack Query
Bridge:     Hono RPC (hc<AppType>) ─ end-to-end 型貫通、codegen 不要
Forms:      React Hook Form + Zod
Compiler:   React Compiler (1.0)
Storage:    Cloudflare R2 (S3 互換、Presigned URL、private bucket) ─ 領収書画像
Deploy:     Fly.io (BE) + Vercel/Pages (FE)
```

## ディレクトリ構成 (feature-based + 3-layer architecture)

monorepo: Bun workspaces (`apps/*` + `packages/*`)。

```
apps/api/                  # Hono BE (@circle/api)
  src/
    index.ts               # entrypoint、各 feature を mount
    lib/                   # cross-cutting concerns
      db/
        central.ts         # Central DB Drizzle client
        tenant.ts          # Tenant DB factory (dynamic connect、Phase 2)
        schema.ts          # Central DB schema の aggregator (auth/schema を re-export、Phase 2+ で他テーブル追加)
      auth/                # better-auth config + schema (Phase 1 完了)
      middleware/          # tenant resolution (Phase 2)
    features/              # feature folders (Phase 1+ で作成)
      <feature>/
        index.ts           # layer 1: HTTP (Hono router、Zod validation)
        service.ts         # layer 2: domain (business logic)
        repository.ts      # layer 3: data (Drizzle queries)
        db.ts              # Drizzle table 定義
        schema.ts          # Zod validation / 型定義
  drizzle/                 # migration files (Central + Tenant)
  drizzle.config.ts
  .env                     # Turso credentials (git ignored)
  .env.example             # placeholder (tracked)

apps/web/                  # Vite + React FE (@circle/web)
  src/
    main.tsx               # RouterProvider + styles.css import
    routes/                # TanStack Router file-based (URL routes)
      __root.tsx
      index.tsx
    routeTree.gen.ts       # auto-generated by @tanstack/router-plugin (tracked)
    lib/                   # cross-cutting
      api.ts               # Hono RPC client (hc<AppType>)
    features/              # feature folders (Phase 1+ で作成)
      <feature>/
        components/
        hooks.ts           # TanStack Query hooks
        schema.ts
    styles.css             # @import "tailwindcss" + @import "@heroui/styles"
  vite.config.ts           # plugins: TanStack Router, React + Compiler, Tailwind v4
                           # server.proxy で /api/* → localhost:3000

packages/shared/           # BE/FE 共通の Zod schemas / types (@circle/shared)

docs/                      # tracked (memo/ だけ git ignored)
  REQUIREMENTS.md          # 要件定義
  ARCHITECTURE.md          # システム設計詳細
  ROADMAP.md               # Phase 構成 / マイルストーン / 落とし穴
  decisions/               # ADR (Architecture Decision Records)
    README.md              # ADR 運用ルール
    NNN-*.md               # 各設計判断
  memo/                    # 一時メモ (git ignored)
```

### 3-layer 依存方向 (BE)

```
index.ts (HTTP) ──► service.ts (domain) ──► repository.ts (data)
```

**逆向き禁止**: repository は service を import しない、service は index を import しない。Pure な一方向依存。

## 開発コマンド

```sh

bun run dev:api          # http://localhost:3000
bun run dev:web          # http://localhost:5173 (Vite proxy で /api/* → BE)

# 型チェック (CI でも回る)

# DB (apps/api 配下で)

bun run db:generate      # drizzle-kit generate (migration SQL 生成)
bun run db:push          # drizzle-kit push (DB に schema 反映)

```

## 重要な設計判断 (詳細は `docs/ARCHITECTURE.md`)

- **DB per tenant** ─ 各サークルに独立した libSQL DB。security 最強 + tenant 単位 backup 容易。Turso が Free で 100 DB / Developer $4.99/月で unlimited なので経済的に成立。
- **法人会計の重さを捨てる** ─ 仕訳・税務・インボイス・freee 連携、全部 NO。"会計知識ゼロで回る" がコンセプト。Expensify / freee の対立軸。
- **Hono RPC 型貫通** ─ `apps/api` から `AppType` export、`apps/web` で `hc<AppType>` import、codegen 不要。
- **HeroUI v3 採用 (shadcn ではない)** ─ React Compiler との二重メモ化問題回避 (TanStack Table v8 ではなく HeroUI Table を使う)。
- **TanStack Router file-based + 型安全** ─ React Router の loader/action 文化を採用せず、TanStack Query で server state 管理。
- **better-auth (Lucia ではない)** ─ Lucia は learning resource 化したため active dev じゃない。better-auth は Hono 公式 adapter + organizations plugin。

## 落とし穴 (Phase 2-4 で必ず当たる、`docs/ROADMAP.md` §6)

- **better-auth organizations を DB per tenant 化**: plugin は前提として "全 tenant data が同一 DB" 想定 ─ Phase 2 で組み合わせ設計工夫必要
- **Turso DB programmatic 作成 rate limit**: 大量 tenant 一気作成すると hit、throttle + retry queue
- **Migration を全 tenant DB に流す pattern**: idempotent migration、進捗を `tenants` table に記録
- **領収書 R2 の Presigned URL 期限切れ**: 5-10 分、FE で期限切れたら再 fetch
- **Bun runtime の npm package 互換性**: 主要 stack (Hono / Drizzle / better-auth / Vite) は対応済み、その他は都度確認

### Process (Phase 1 から導入、Phase 2 で運用調整)

- **Branch / PR 運用 (案 B)**: **実コード変更 (`apps/api`, `apps/web`, `packages/*`) は branch + PR 経由で main に merge**。**doc / ADR / chore / 整合性更新 (`docs/`, `.github/`, `CLAUDE.md`, README) は main 直 push** で OK。判断軸: 「コード動作を変えるか」「LoC > 50 か」「auth / DB / RBAC に触るか」のどれかに yes なら PR、それ以外は直 push
- **ADR**: 設計判断は `docs/decisions/` に残す (運用ルールは `docs/decisions/README.md`)
- **PR template**: `.github/PULL_REQUEST_TEMPLATE.md` の What / Why / How tested を埋める
- **CI**: GitHub Actions で push & PR に `bun run typecheck` が走る (`.github/workflows/ci.yml`)。**直 push でも main に CI は走る**
- **Self-review**: PR 立てたら自分で diff を一度通読してから merge
- **Merge 戦略**: PR は **rebase merge** (atomic な commit 履歴を main に linear に残す)。merge 後は `--delete-branch` で remote branch も整理
- **AI review 運用** (PR 経由の時のみ):
  - 実装系 (普通): merge 前に `/code-review` (medium effort) を Claude が会話の中で実行
  - 実装系 (大型 / 危険 / security touch / DB schema 変更 / リファクタ): あさひが `/ultrareview <PR#>` を手動起動
  - 判断軸: LoC 100行超え or 複雑 logic は AI review 入れる、auth / payment / file upload / RBAC は必ず、迷ったら厚め
